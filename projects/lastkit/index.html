Overview

Creating a design system for a secure and private domain was never an easy project. The main problem to start with was the fragmented UI, the increasing tech debt and the inability to provide a consistent user experience throughout the whole product line. I had those factors in mind throughout the whole project of creating the LastKit Design System.

  • Reduce tech debt
  • Improve security
  • Increase developer velocity

The problem

LastPass is stepping up on the maturity steps as a SaaS tool and B2B-focused company, and needs a better approach to unify its design and frontend architecture solutions.

I played a key role in founding the design system for such a difficult domain.

“As an engineer, I struggle to improve the UI due to the tech debt we are constantly adding to.”
“I cannot find the screens I need in Figma. Searching for the most up-to-date version takes ages...”
“As a Product Owner, it’s pretty hard for me to keep my projects in sync with other clusters, as we are moving with different velocity and keep getting overhead issues.”

Colleagues were identified as our main customers, and we had to fulfil their requirements.

Research & Discovery

As building a design system was not a conventional design project, we decided to take a bit of a twist on the original Double Diamond approach, starting with talking to our customers and identifying their needs.

We discovered that they are in desperate need of a complex yet easy-to-implement library of components, so everyone works with a single source of truth.

User interviews

I started by talking to our customers, asking in a way that let them communicate their needs.

The takeaway was clear. Our users need a better and more efficient way of working with both design and code.

Sketching & Ideation

After we got our main information and entry points, we started to work on the details and how we should approach the project.

We tried out many options, both for frontend technologies and for design solutions.

How the LastKit Design System was built

It was quite a journey, let’s hop in with me!

The picture above shows the finalized documentation site, but there was still a great deal to be done before reaching that point.

The starting point

I started with creating a list of components I needed to create in Figma. Not just creating components randomly, but auditing our products and creating use cases where the UI element is being used. The key when deciding whether to create a component was reusability. Are we going to use it again and again, or is it just a simple entity that lives in the system?

The nature of a library like this is that it’s never finished and will grow organically in the future. The starting set was around 25 components. I kept different types of information in different files, like foundations and components.

Let’s continue with some coding

We started working on our coded components in 2023–24 and created a library for our web teams to use. To implement components into legacy code, we needed the teams to update to a certain version of React. We decided to go with React as it’s a common solution for design systems and it’s future-proof.

Our goals with the libraries

The product line is diverse and has a lot of tech debt as a result of not having a consistent way of working. On top of that, components were not being used anywhere in code.

We realised that creating a library in Figma and in code wouldn’t be enough to solve the problems of the product. We needed to unify the frontend codebase.

Accessibility was nowhere near the level we needed. To meet the WCAG 2.1 international technical standard for web accessibility, we required our components to be implemented in an accessible way.

The challenges

We faced many challenges from time to time.

Challenge

The main issue was how to demonstrate that the effort we are putting into this project will eventually pay off.

Solution

We proved ourselves by significantly reducing the time required for creating new designs by using our design system library.

Challenge

The stakeholders wanted to see if the design system would be useful for engineers as well, and how it can help reduce the time developers require to ship a finished product.

Solution

We started with testing our coded components with a feature in our web application. It was a great success, as we reached the MVP state of the product 30% quicker than originally estimated. It was our first GA in-product use case of LastKit.

Challenge

How can we spread the word in the company about the LastKit design system and get everyone on board? It was not easy to convince devs and designers to change from the old ways to the new way of working.

Solution

We held workshops, held our users’ hands and kept them busy with news about the design system weekly. Supporting my colleagues was key for me to keep momentum of spreading the word and getting the benefits of LastKit.

Current state of the design system

Currently the LastKit design system has 40+ fully designed and built components in 4 different themes. Documentation is done in a brand-new documentation site in GitLab. We separated the different fields of the system into categories like Components, Themes and Patterns to cover each segment efficiently without creating a massive single-file solution.

All available for our designers and engineers to improve the products they are working on. Documented in blueprints dedicated to each component; for engineers we created the documentation site.

New challenge along the way

When we were working on the libraries, the company served us great news. We are going to do a brand refresh in a year. That meant we had to keep the existing components with the current design while creating a new library with the refreshed variables, tokens and styles. Now that was something we had to figure out: running multiple systems simultaneously. We successfully implemented the brand new design while not breaking the current working files.

Where LastKit was being used

I’m proud that we used LastKit in the Web application, Desktop application, VPN application and the Unified Admin Console. Also proud that we shipped a product that has successfully proved itself in a live environment where 30+ million users enjoyed using LastPass seamlessly, without any delays or issues, while we updated the codebase. It was like changing the engine in a flying airplane.

Impact & Results

We successfully reduced our tech debt and built a system that our internal users can use daily. By creating a consistent user experience, we established an ecosystem where our external users, both B2C and B2B, feel secure and are in a safe space to progress with their life.

  • Reduced tech debt by 70%*
  • Developer velocity increased by 65%*
  • NPS score increased

*Metrics based on time required to implement and publish a new feature in our products using the LastKit Design System.
